# FlowLedger

CDC для одной таблицы PostgreSQL: согласованный начальный снимок, поток изменений WAL через RabbitMQ и отдельная база проекций. Проект показывает восстановление на границах трёх систем, включая повторную доставку и потерю replication slot.

## Возможности

- Копирование `public.items` порциями по 500 строк из экспортированного снимка replication slot. Записи во время копирования затем приходят через WAL.
- Чтение `pgoutput` v1: вставки, обновления, удаления и `TRUNCATE`. Смена первичного ключа и неизменившиеся значения TOAST сохраняются корректно.
- Доставка транзакций через постоянную очередь RabbitMQ с publisher confirms. Позиция издателя сохраняется после подтверждения брокером; затем подтверждается WAL.
- Изменения проекции и её позиция LSN фиксируются одной транзакцией. Повтор уже применённой транзакции не меняет результат; сообщение подтверждается после коммита.
- Новый снимок при потере слота, незавершённом копировании или изменении поддерживаемой схемы. Поколение снимка отделяет его от сообщений старой очереди.
- Один издатель под advisory lock и один активный потребитель очереди. Полная автоматическая сверка источника и проекции после восстановления.

Стек: Python 3.11+, PostgreSQL 17, psycopg 3 для SQL, psycopg2 для replication connection, RabbitMQ, pika, pytest, Ruff, Docker Compose, GitHub Actions. HTTP API не требуется: управление и проверка выполняются через CLI и SQL.

## Запуск

Нужны Docker с Compose и uv. Все опубликованные порты привязаны к `127.0.0.1`; данные и пароли в примере учебные.

```bash
git clone https://github.com/dasferwer/flowledger.git
cd flowledger
cp .env.example .env
uv sync --frozen
set -a
. ./.env
set +a
docker compose up --build -d
uv run python -m scripts.status
```

Первый запуск создаёт 5000 строк источника. Дождитесь `status: ready`; при первом старте RabbitMQ издатель может несколько раз повторить подключение. Поля `published_lsn` и `applied_lsn` — числовое представление LSN, а не счётчики строк. `ready` означает завершённый снимок, но не отсутствие задержки доставки.

```bash
docker compose exec -T source psql -U demo -d source -c "UPDATE items SET payload='Обновлено', version=version+1 WHERE id=100;"
uv run python -m scripts.status
docker compose exec -T target psql -U demo -d projection -c "SELECT p.data FROM projection p JOIN state s ON p.generation=s.generation WHERE s.status='ready' AND p.id=100;"
```

Читать нужно только текущее поколение со статусом `ready`. Во время пересборки доступность проекции уступает её согласованности; частичный снимок не следует выдавать пользователю. Между независимыми SQL-запросами источник может измениться, поэтому проверять равенство всей таблицы нужно после остановки записи и завершения доставки.

Настройки перечислены в `.env.example`: `SOURCE_URL`, `TARGET_URL`, `AMQP_URL`; `COPY_DELAY` задаёт паузу между порциями снимка. Compose использует собственные адреса сервисов и паузу 0,05 секунды для демонстрации записи во время копирования. Локально процессы можно запускать командами `uv run python -m flowledger.publisher` и `uv run python -m flowledger.projector`, предварительно остановив соответствующие контейнеры.

## Проверки

После запуска стенда и загрузки `.env`:

```bash
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
uv run python -m scripts.recovery
```

Тесты проверяют декодирование, повторы, старые поколения, атомарный откат позиции вместе с данными, частичные обновления, смену ключа и `TRUNCATE`. PostgreSQL-тесты создают отдельную временную схему.

Сценарий `scripts.recovery` предназначен только для этого учебного стенда: изменяет данные `items`, останавливает его контейнеры, удаляет текущий слот проекта и добавляет текстовую колонку. Он пишет во время снимка, останавливает потребителя, завершает издателя через SIGKILL, проверяет восстановление после потери слота и изменения схемы. После этапов сравниваются все строки и все значения, а не только количество. Повторный запуск допустим; каждый добавляет новую колонку. Не запускайте сценарий одновременно с другим экземпляром или внешней записью в источник.

CI выполняет линтер, проверку форматирования, тесты и этот сценарий на Python 3.11 с настоящими PostgreSQL и RabbitMQ. Локальные результаты записаны в [VERIFICATION.md](VERIFICATION.md).

Остановка с сохранением данных: `docker compose down`.

## Гарантии и ограничения

Поддерживается одна таблица `public.items`, первичный ключ только `id bigint`, столбцы типов `smallint`, `integer`, `bigint`, `boolean`, `text`, `varchar`. `REPLICA IDENTITY FULL` и publication задаются в `sql/source.sql`. Изменение поддерживаемой схемы приводит к полному пересозданию снимка; универсальной миграции DDL нет. Неподдерживаемые типы и сообщения останавливают обработку с ошибкой. Двухфазные и потоковые большие транзакции не реализованы.

Транзакция буферизуется до 10 000 изменений или 8 МиБ исходных сообщений. Превышение останавливает продвижение позиции, а не пропускает данные. Необходимо устранить причину вручную; за размером WAL и состоянием слота должен следить оператор. Большой снимок также удерживает WAL.

Доставка допускает повторы, а применение в проекции идемпотентно по поколению и LSN. Это не глобальная гарантия exactly-once для внешних побочных эффектов. Подтверждение источнику следует за сохранением в брокере, не за применением проекции. Полная потеря диска RabbitMQ после подтверждения может потребовать нового снимка: автоматического обнаружения такого случая нет. Обычная остановка потребителя сохраняет очередь на Docker volume.

Старые поколения остаются в базе; сборка мусора, кластерный RabbitMQ, отказоустойчивость PostgreSQL, метрики и промышленная настройка прав не входят в проект. Стенд использует учебного суперпользователя PostgreSQL. Потеря слота восстанавливает актуальное состояние таблицы, но не историю всех пропущенных изменений.

Формат протокола и снимков описан в документации [PostgreSQL](https://www.postgresql.org/docs/17/protocol-logicalrep-message-formats.html), [replication protocol](https://www.postgresql.org/docs/17/protocol-replication.html) и [psycopg2](https://www.psycopg.org/docs/extras.html).
